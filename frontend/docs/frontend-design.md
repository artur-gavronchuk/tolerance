# Технический дизайн фронтенда

Версия 0.1 · 17 сентября 2026 · проектное решение для срезов 1–5.

Фронт — отдельное приложение в репозитории `tolerance-front`, со своим деплоем и своим доменом. Оно общается с бэкендом только по HTTP API из [backend-design.md](backend-design.md), не имеет серверной части и не хранит секретов. Локальный vanilla-JS интерфейс из прототипа не переносится; переносятся его экраны как отправная точка для разделов «Миссии», «Приёмка», «Выпуски», «История».

## 1. Стек

| Область | Решение | Почему |
|---|---|---|
| Сборка | Vite, TypeScript strict | статика без серверного рендеринга; публичный отчёт отдаёт бэкенд как снимок, SSR не нужен |
| UI | React 19 | договорённость архитектуры |
| Роутинг | TanStack Router, файловые роуты, типизированные параметры и `loader` | роуты кабинета зависят от роли и id; ошибки типов в ссылках ловятся при сборке |
| Серверное состояние | TanStack Query | кэш, инвалидация по SSE, повтор запросов, `staleTime` по типу объекта |
| API-клиент | `openapi-typescript` + `openapi-fetch` из `contracts/openapi/openapi.yaml` бэкенда | один источник форм; ручных типов ответов нет |
| Вход | `oidc-client-ts`, Authorization Code + PKCE | SPA на отдельном домене, без cookie и CSRF; api проверяет JWT по JWKS |
| Формы | `react-hook-form` + `zod` | схемы полей повторяют ограничения OpenAPI, ошибки `fields[]` от api подставляются по `path` |
| Стили | Tailwind CSS 4 + собственные компоненты на Radix Primitives | доступность диалогов, меню и вкладок без тяжёлого UI-кита; визуальный язык свой |
| Тесты | Vitest + Testing Library, MSW, Playwright | см. раздел 9 |
| Пакетный менеджер | pnpm | lockfile, быстрая установка в CI |

Дата и время: `Intl.DateTimeFormat` с часовым поясом пользователя, рядом всегда UTC в `title`. Числа в баллах с одним десятичным знаком, деньги из минимальных единиц по валюте кампании. Никаких float-вычислений на клиенте: баллы и суммы приходят от api уже посчитанными.

    auth/

      organizer/          готовность, очередь, расходы, публикация
      public/             сезон, отчёт, сравнение A/B/C, демо

Правило для `features/*`: модуль экспортирует страницы-компоненты и хуки, а данные получает только через `api/queries` и `api/mutations`. Компонент не вызывает `fetch` сам. `ui/*` не знает о доменных типах.

## 3. Роуты

Карта интерфейса из `foundation.md` разворачивается в файловые роуты. Скобки — layout-роуты без сегмента пути.

```text
routes/
  __root.tsx                       ErrorBoundary, NotFound, провайдер темы
  index.tsx                        редирект: авторизован → /campaigns, иначе → /public
  login.tsx · auth/callback.tsx · logout.tsx
  (public)/
    public/index.tsx               список опубликованных сезонов
    public/campaigns/$slug.tsx     сезон: задача, этап, сроки, продукты
    public/campaigns/$slug/report.tsx
    public/campaigns/$slug/compare.tsx   анонимные варианты A/B/C
  (app)/                           guard: сессия + активная организация
    _app.tsx                       shell: боковая навигация, переключатель организации, роль
    campaigns/index.tsx
    campaigns/$campaignId/index.tsx      что происходит: этапы, сроки, результаты
    campaigns/$campaignId/entries.tsx
    campaigns/$campaignId/appeals.tsx
    campaigns/$campaignId/scoreboard.tsx
    campaigns/$campaignId/audit.tsx
    missions/$missionId.tsx              что нужно доказать: требования, версии, правила, бюджет
    missions/$missionId/versions/$n.tsx
    workspace/entries/$entryId.tsx       что осталось сдать: квалификация, агент, версии, сдачи
    workspace/entries/$entryId/submit.tsx мастер сдачи
    submissions/$submissionId.tsx        что проверили: артефакт, происхождение, матрица
    evaluations/$evaluationId.tsx        матрица и свидетельства
    decisions/$decisionId.tsx            решение, ревизии, спор
    appeals/$appealId.tsx                спор и разрешение
    runs/$runId.tsx                      попытки, состояние, затраты, отмена
    projects/$projectId/releases.tsx     что выдержало изменение
    participants/$teamId.tsx             что участник доказал
    compare/$campaignId.tsx              сравнение внутри организации, с авторами
    organizer/campaigns/$campaignId/     guard: role in (organizer, owner)
      index.tsx                          готовность к следующему этапу
      calibration.tsx
      budget.tsx
      sessions.tsx                       назначения слепых сессий
      publish.tsx                        ревизии отчёта и публикация
    settings/organization.tsx            члены, приглашения
```

Guard'ы в `beforeLoad`: `(app)` требует аутентификацию и выбранную организацию; `organizer/*` требует роль; страницы участника проверяют, что entry принадлежит команде пользователя, иначе api вернёт 404 и роут покажет «Объект недоступен». Клиентская проверка роли только прячет действия; право решает сервер.

`loader` каждого роута вызывает `queryClient.ensureQueryData(queryOptions)`; страница рендерится с данными, `pending`-состояние показывает скелет не дольше 300 мс.

## 4. Данные и состояние

Три вида состояния и их место:

| Состояние | Где | Пример |
|---|---|---|
| Серверное | TanStack Query | кампании, миссии, сдачи, матрицы |
| Сессия | `auth/session.ts` (небольшой store на `useSyncExternalStore`) | пользователь, токен в памяти, активная организация в `localStorage` |
| Локальное UI | `useState`, URL search params | открытая вкладка, фильтры таблиц, шаг мастера |

Ключи запросов: `['campaign', id]`, `['campaign', id, 'missions']`, `['submission', id]`, `['evaluation', id, 'matrix']` и так далее, всегда с `organizationId` первым элементом, чтобы смена организации сбрасывала кэш целиком.

`staleTime`: опубликованные версии контракта, артефакты и финальные решения — `Infinity` (неизменяемы по правилам); списки и активные объекты — 15 секунд; всё, что приходит по SSE, инвалидируется точечно.

SSE: страница кампании и её потомки подписываются на `/campaigns/{id}/events` через `lib/sse` (потоковый `fetch` с заголовком `Authorization`, `Last-Event-ID`, экспоненциальный повтор до 30 секунд). Событие `{kind, id, version}` инвалидирует ключ агрегата и списки, в которые он входит. Данные в событии не используются для рендера.

Мутации: каждая команда генерирует `Idempotency-Key` через `crypto.randomUUID()` один раз при открытии формы и переиспользует его при повторной отправке той же формы после сетевой ошибки; новая форма — новый ключ. Ответ `409 state_conflict` перечитывает объект и показывает актуальную версию с предложением повторить. `422` раскладывает `fields[]` по полям формы. `409 budget_unavailable`, `409 gate_failed`, `409 official_slot_taken` показываются как блокирующие сообщения с текстом от api.

## 5. Вход и организации

1. `/login` → `UserManager.signinRedirect()` с PKCE к OIDC-провайдеру из `config.json`.
2. `/auth/callback` → `signinRedirectCallback()`; access token хранится только в памяти `UserManager`. Обновление — refresh token с ротацией, если провайдер выдаёт его публичному клиенту; иначе silent renew в скрытом iframe, который ломается при блокировке сторонних cookie, поэтому провайдер выбирается с ротацией refresh token.
3. `GET /me` → членства. Если одна организация — выбирается сама; иначе экран выбора. Выбор хранится в `localStorage`, отправляется в `X-Organization-Id`.
4. `401` от api → попытка silent renew → при неудаче редирект на `/login` с возвратом на исходный URL.
5. Выход: `signoutRedirect()`, очистка кэша Query и `localStorage`.

Приглашение: ссылка `/invitations/$token` доступна без организации, после входа вызывает `POST /invitations/{token}/accept` и переключает организацию.

## 6. Ключевые экраны

Каждый экран отвечает на один вопрос из карты интерфейса; ниже состав и правила отображения.

**Кампания** (`campaigns/$campaignId`). Заголовок с режимом (`public_season` / `private_trial`) и состоянием. Лента этапов: для каждой миссии stage, состояние, дедлайны, число сдач и решений. Блок «Что делать дальше» зависит от роли: владелец видит ожидающие решения, участник — открытые слоты сдачи, организатор — блокирующие условия. Внизу ссылки на споры, баллы, журнал.

**Миссия** (`missions/$missionId`). Активная версия контракта: бриф, таблица требований с `stable_key`, `gate`, весом; правила ресурсов, приёмки и публикации; `contract_digest` с кнопкой «пересчитать в браузере» (канонический JSON и SHA-256 через WebCrypto, совпадение показывается явно). Переключатель версий; различия между версиями подсвечиваются по `stable_key`. Действия: организатор — «Открыть» с проверкой калибровки, «Закрыть приём», «Финализировать»; участник — «Перейти к сдаче».

**Рабочее место участника** (`workspace/entries/$entryId`). Квалификация, зарегистрированные версии агента с digest манифеста, слоты официальных сдач `(миссия × повторение)` со статусом «свободен / сдан / оценивается / решение», диагностические сдачи отдельным списком. Для управляемого режима — кнопка запроса запуска и список попыток.

**Мастер сдачи** (`workspace/entries/$entryId/submit`). Шаги: 1) выбор миссии, повторения, родительской сдачи для `adapt`; 2) манифест по форме из JSON Schema с валидацией на клиенте; 3) загрузка пакета: `POST /uploads` → PUT в S3 с прогрессом → SHA-256 считается потоком в Web Worker параллельно → `complete` с digest; 4) подтверждение: «после фиксации исправление не заменит результат». Незавершённая загрузка сохраняет `upload_id` в `sessionStorage`, чтобы переоткрытие вкладки продолжило, а не создало вторую.

**Сдача** (`submissions/$submissionId`). Сверху статус: `принят / не принят / проверка не завершена`. Артефакт: digest, размер, ссылка «скачать» через `artifact-url`. Происхождение: агент, режим, попытка, заявленная помощь, `coverage` затрат. Список оценок с официальной, помеченной явно.

**Матрица оценки** (`evaluations/$evaluationId`). Таблица «требование → статус → сценарии → свидетельства». Обязательные требования сверху, `fail` и `error` выделены разным цветом и текстом; `error` подписывается «проверка не состоялась», `skipped` — причиной. `failure_origin` показывается всегда, `unknown` — словом «не установлено». Свидетельство открывается в панели: скриншоты как изображения по краткоживущему URL, trace — кнопка скачать, логи — текст в `<pre>` с экранированием; HTML никогда не вставляется. Пометка объёма проверки из `scope_note` над таблицей. Кнопка «Решение» для владельца, если оценка `completed`.

**Решение** (`decisions/$decisionId`). Форма: допуск, приёмка, причины по требованиям, перечень учтённых результатов. Принять нельзя, если есть обязательное требование без `pass`: кнопка недоступна с объяснением, api всё равно проверит. Ревизии в хронологии; старая ревизия читается целиком. Кнопка «Оспорить» в окне споров.

**Спор** (`appeals/$appealId`). Требование, сдача, решение, ожидаемое поведение, приложенные свидетельства. Арбитр видит три исхода и обязан написать причину. `needs_recheck` показывает список затронутых сдач и предупреждение о резерве организатора.

**Запуск** (`runs/$runId`). Состояние попыток по машине состояний, heartbeat, затраты с `coverage`, кнопка «Отменить» с текстом «отмена подтверждается после остановки среды». `reconciliation_required` показывается красным с инструкцией для оператора; клиент ничего не «чинит».

**Выпуски** (`projects/$projectId/releases`). Цепочка выпусков сверху вниз с `previous_release_id`, каждая карточка — сдача, решение, digest, события (`revoked`, `superseded`, `note`). Сравнение двух выпусков: требования с `stable_key`, статус тогда и сейчас, регрессии выделены.

**Баллы** (`campaigns/$campaignId/scoreboard`). Таблица по регламенту: допуск, build 1 / build 2 / среднее, adapt 1 / adapt 2 / среднее, UX, итог. `pending` отображается словом, не нулём; неизмеренные расходы — «не измерено». Итог сезона не показывается как финальный, пока api не вернёт `finalized`.

**Организатор** (`organizer/campaigns/$campaignId`). Чек-лист открытия из регламента с автоматически проверяемыми пунктами (калибровка, бюджет, роли, скрытые пакеты зафиксированы) и ручными галочками с автором. Очередь оценок и запусков, возраст, `reconciliation_required`. Расходы по статьям против лимита. Публикация: ревизии, предпросмотр очищенного снимка, список исключённых частей, кнопка «Опубликовать» с подтверждением.

**Публичный сезон** (`public/campaigns/$slug`). Читает только `public_projection`. Продукты обозначены A/B/C до раскрытия. Демо открываются ссылкой на демо-домен в новой вкладке; ничего из сессии платформы не передаётся. Истёкшее демо показывает запись и отчёт.

## 7. Дизайн-система

`ui/*` — свои компоненты на Radix Primitives, стили Tailwind, токены в `:root` и `[data-theme=dark]`. Обязательные элементы:

- `StatusPill` — единая семантика для всех статусов платформы: `pass`, `fail`, `error`, `skipped`, `pending`, `accepted`, `rejected`, `provisional`, `final`, состояния миссий и попыток. Цвет плюс текст плюс иконка, никогда только цвет.
- `Hash` — digest с первыми 12 символами, копированием и полным значением в `title`.
- `Timestamp` — локальное время, UTC в подсказке, относительное «3 минуты назад» только в лентах.
- `Money` — минимальные единицы → строка по валюте; рядом `coverage` бейджем.
- `DataTable` — сортировка, cursor pagination, пустое состояние с объяснением.
- `Empty` — заголовок и следующее действие, как в прототипе.
- `Dialog`, `ConfirmDialog` — для необратимых команд (открыть миссию, зафиксировать сдачу, решение, публикация) с текстом последствия.

Доступность: все интерактивные элементы с клавиатуры, `aria-live` для сообщений об операциях, контраст не ниже AA. Верстка работает от 360 px; таблицы на узких экранах превращаются в карточки.

## 8. Конфигурация и деплой

Одна сборка на все окружения. Параметры читаются при старте из `public/config.json`:

```json
{
  "apiBaseUrl": "https://api.forge.example",
  "oidc": {"authority": "https://id.example/realms/forge", "clientId": "forge-web", "scope": "openid profile email"},
  "demoDomain": "forge-apps.example"
}
```

Деплой: `pnpm build` → каталог `dist/` → контейнер nginx или bucket за CDN. Fallback на `index.html` для всех путей кроме `/config.json` и `/assets/*`. Заголовки nginx:

```text
Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';
  img-src 'self' data: https://<evidence-cdn>; connect-src 'self' https://api.forge.example https://id.example;
  frame-src https://id.example; frame-ancestors 'none'; base-uri 'none'
X-Content-Type-Options: nosniff
Referrer-Policy: no-referrer
```

`'unsafe-inline'` для стилей нужен Radix Primitives, которые позиционируют всплывающие элементы через атрибут `style`; скрипты инлайн запрещены. Ассеты с хешем в имени кэшируются год, `index.html` и `config.json` — `no-cache`.

CI: `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`, e2e на compose-стенде по метке. Генерация клиента `pnpm api:generate` берёт `openapi.yaml` из бэкенда по зафиксированному тегу; расхождение типов ломает `typecheck`, и это желаемое поведение.

## 9. Тестирование

| Уровень | Что | Как |
|---|---|---|
| Unit | форматирование, digest, парсер SSE, guard'ы, маппинг ошибок | Vitest |
| Компоненты | матрица оценки, мастер сдачи, решение с недоступной кнопкой при непройденном gate, статусы | Testing Library + MSW с ответами из примеров OpenAPI |
| Контракт | сгенерированный клиент соответствует текущему `openapi.yaml` | `typecheck` в CI |
| E2E | путь «владелец публикует → участник сдаёт эталонный пакет → оценщик проверяет → владелец принимает → второй выпуск»; чужая организация не видит объект; загрузка после дедлайна отклонена | Playwright против compose-стенда с Dex и fixtures |

Тесты, которые фиксируют правила доверия интерфейса: `error` никогда не отображается как `fail`; `pending` никогда как ноль; HTML из свидетельств не рендерится; артефакт скачивается по URL от api, а не собирается на клиенте.

## 10. Порядок реализации по срезам

| Срез | Экраны | Готово, когда |
|---|---|---|
| 1 | вход, организации, кампания, миссия, версии контракта, организатор (открытие), журнал | владелец публикует контракт из интерфейса; пересчёт digest совпадает |
| 2 | рабочее место, мастер сдачи с загрузкой, сдача, матрица, свидетельства, решение, спор, SSE | внешний пакет проходит до принятого выпуска через интерфейс |
| 3 | выпуски и сравнение, баллы, родительская сдача в мастере | регрессия видна на экране сравнения; история не переписывается |
| 4 | запуски, попытки, отмена, вмешательства, расходы | оператор видит `reconciliation_required` и подтверждённую отмену |
| 5 | пользовательские сессии, калибровка, публикация, публичный сезон, сравнение A/B/C, участники | публичный отчёт открывается без входа и не содержит закрытых частей |

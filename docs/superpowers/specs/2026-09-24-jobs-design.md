# Срез 3: заказы

> **Отложено 25 сентября 2026.** Биржа (заказы, деньги, автопилот) снята с главного направления, см. раздел «Пересмотр 25 сентября» в `2026-09-23-platform-roadmap.md`. Спека сохранена как гипотеза и не исполняется.

24 сентября 2026. Строится поверх срезов 1 и 2. Решения приняты автором по поручению владельца.

## 1. Что строим

Вторая сторона рынка. Заказчик публикует задачу на своём публичном репозитории с приёмочными тестами и покупает N независимых попыток. Агенты с подтверждённым направлением и достаточным доступом видят заказ, берут слот, решают у владельца, платформа проверяет каждое решение в песочнице и показывает заказчику сравнение. Заказчик принимает одно решение и скачивает патч. Расчёт в тестовых кредитах через двойную запись, настоящих денег нет (срез 4).

**Цикл заказчика:** «Hire» → описать задачу → репозиторий и коммит → загрузить приёмочные тесты → бюджет и число попыток → автопроверка тестов на исходном коде → модерация → заказ открыт → решения приходят → сравнение → «Принять» → патч.

**Цикл владельца агента:** «Work» → доступные заказы и заблокированные с причиной → «Взять» → агент работает у владельца → результат → если выбран: кредиты.

Вне среза: деньги и выплаты, комиссия, приватные репозитории, автопилот, споры и апелляции, языки кроме Go и Python, влияние заказов на рейтинг (срез 4).

## 2. Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Кто заказчик | Любой пользователь; отдельной роли нет, `jobs.customer_user_id` | Один аккаунт может и нанимать, и владеть агентом |
| Репозиторий | Только публичный GitHub: `owner/repo` + ветка или SHA; при создании ветка превращается в SHA через `api.github.com/repos/{o}/{r}/commits/{ref}`, архив берётся с `codeload.github.com/{o}/{r}/tar.gz/{sha}` и хранится у нас | Проверено: gzip-тарбол с одной верхней папкой `{repo}-{sha}/` и SHA в pax-заголовке `comment`; приватный или несуществующий → 404. Фиксированные хосты исключают SSRF |
| Лимиты архива | 20 MiB сжатого, 100 MiB распакованного, до 20 000 файлов; симлинки и жёсткие ссылки отбрасываются | Защита диска и распаковки |
| GitHub rate limit | Без токена 60 запросов/час на IP; `ARENA_GITHUB_TOKEN` (опционально) поднимает до 5000 | Проверено в API |
| Приёмочные тесты | Zip с тестовыми файлами, пути от корня репозитория, до 1 MiB; накладываются поверх репозитория перед прогоном; агент их не видит | Тот же механизм, что `_hidden` в задачах платформы |
| Какие тесты приёмочные | Go: функции `^func (Test\w+)\(` из наложенных файлов; Python: node id с путём наложенного файла | Отделяем тесты заказчика от тестов репозитория |
| Зависимости | Для каждого заказа собирается образ: базовый образ языка + репозиторий + `go mod download` или `pip install -r requirements.txt` с сетью, лимит 10 мин и 2 GiB; прогоны решений идут в этом образе без сети; образ удаляется при закрытии заказа | У реальных репозиториев есть зависимости, а песочница без сети |
| Автопроверка (preflight) | Прогон приёмочных тестов на исходном коде: должен найтись ≥1 приёмочный тест, ≥1 приёмочный тест должен падать, прогон укладывается в таймаут. Результаты сохраняются как базовая линия | Тесты, которые уже зелёные или ничего не находят, — не задача |
| «Решено» | Все приёмочные тесты проходят И ни один тест репозитория, проходивший на базовой линии, не упал | «Починил и ничего не сломал» — понятное заказчику определение |
| Модерация | После preflight заказ ждёт одобрения администратора, только потом открыт | Сборка образа исполняет код заказчика с сетью; кураторская бета защищает и от злоупотреблений, и от мусорных заказов |
| Попытки | 1, 3 или 5 слотов; один агент — один слот в заказе | Механика «покупаю вероятность хорошего решения» |
| Вознаграждение | Победитель получает `bounty`; каждый другой слот с «решено» получает 15% `bounty` (бонус финишёра); заказчик резервирует `bounty × (1 + 0.15 × (N − 1))`, неиспользованное возвращается | Без бонуса мультипопыточные заказы — лотерея за чужой compute |
| Выбор победителя | Заказчик выбирает в течение 72 часов после закрытия приёма. Если есть хотя бы одно «решено» и заказчик молчит, платформа принимает лучшее: больше приёмочных pass → меньше регрессий → меньше строк diff → раньше сдано | Защищает агентов от заказчика, который пропал |
| Нет «решено» | Заказчик может принять частичное решение (платит `bounty`) или закрыть без победителя (резерв возвращается полностью) | Честно для обеих сторон |
| Доступ к заказу | Направление заказа `verified` на текущей версии агента и потолок доступа ≥ `bounty`. Потолок — формула Arena42 как есть: `access 1500..1800 → 80..160`, `1800..2100 → 600..1000`, `2100..2400 → 1000..2000` (кредиты) | Roadmap, решение 2 |
| Кредиты | Двойная запись в `ledger_entries`, валюта `CRD`, суммы в центах; начисления делает администратор | Срез 4 добавляет реальную валюту к той же книге, а не переписывает учёт |
| Одна работа за раз | Индекс «одна открытая проверка на агента» из среза 1 не меняется: агент с открытым заказом не может взять второй | Параллельность — в срезе 6 вместе с автопилотом |
| Результат для заказчика | Патч (`git diff`) и инструкция `git apply`; видны имена приёмочных тестов (это тесты заказчика) | Заказчик получает артефакт, который применяет у себя |

## 3. Домен

### 3.1. Сущности

- `jobs`: `id`, `customer_user_id`, `title`, `description` (markdown, до 20 000 символов), `acceptance_notes` (что проверяют тесты, текст для агента), `skill_slug`, `repo_owner`, `repo_name`, `repo_ref`, `commit_sha`, `repo_tar` (bytea, без верхней папки), `tests_tar`, `acceptance_tests` (text[]), `run_cmd`, `agent_timeout_s` (1800–14400), `sandbox_timeout_s` (60–900), `bounty_cents`, `attempts_wanted` (1|3|5), `reserve_cents`, `deadline_at`, `status`, `status_reason`, `image_tag`, `baseline` (jsonb), `created_at`, `published_at`, `closed_at`, `accept_by`, `winner_attempt_id`.
- `job_attempts`: `id`, `job_id`, `agent_id`, `version_id`, `proof_id` (текущий прогон), `status` (`running | evaluated | withdrawn`), `acceptance_passed`, `acceptance_total`, `regressions`, `solved` (bool), `diff_added`, `diff_removed`, `files_changed`, `outcome` (`picked | finisher | unpaid | null`), `payout_cents`, `created_at`, `evaluated_at`. Уникально `(job_id, agent_id)`.
- `proofs.kind` получает значение `job` и колонку `job_attempt_id`.
- `ledger_accounts`: `id` (`user:{uid}:available`, `user:{uid}:reserved`, `system:grants`), `currency`. `ledger_entries`: `id`, `tx_id`, `account_id`, `amount_cents` (±), `currency`, `kind` (`grant | reserve | release | payout | finisher`), `ref` (job/attempt id), `created_at`. Инвариант: сумма по `tx_id` = 0. Баланс = сумма по счёту.

### 3.2. Жизненный цикл заказа

`draft → preflight → preflight_failed | pending_review → open → awaiting_acceptance → accepted | closed_no_winner`; из `draft | preflight_failed | pending_review | open` возможно `cancelled`.

1. `draft`: заказчик создал, репозиторий импортирован, тесты загружены.
2. `POST /jobs/{id}/submit`: резерв `reserve_cents` с `available` на `reserved` (не хватает → 402 `insufficient_credits`), статус `preflight`, job `preflight_job`.
3. Воркер: собирает образ, прогоняет тесты на исходном коде, пишет `baseline`. Нарушено правило → `preflight_failed` с причиной (`no_acceptance_tests`, `acceptance_already_passing`, `build_failed`, `timeout`), резерв возвращается. Иначе `pending_review`.
4. Администратор одобряет → `open`, `published_at`, `deadline_at = now + deadline_hours` (2–168) — или отклоняет с причиной → `cancelled`, резерв возвращается.
5. `open`: агенты берут слоты. Приём закрывается при заполнении всех слотов и завершении всех попыток или при `deadline_at`. Попытка, не сдавшая результат к `deadline_at + agent_timeout_s`, истекает.
6. `awaiting_acceptance`, `accept_by = closed_at + 72h`. Заказчик принимает попытку → `accepted`; или закрывает без победителя (только если нет «решено») → `closed_no_winner`. По `accept_by` воркер делает автопринятие или, если «решено» нет, закрытие без победителя.
7. Расчёт при `accepted`: победителю `bounty`, финишёрам по 15%, остаток резерва возвращается. При `closed_no_winner` резерв возвращается целиком.

### 3.3. Жизненный цикл попытки

`POST /jobs/{id}/take`: агент владельца `operational`, online, направление verified на текущей версии, потолок ≥ bounty, нет открытой проверки, слоты есть, заказ `open` и до `deadline_at` больше `agent_timeout_s`. Создаётся `job_attempts` и `proofs` (`kind = job`) в `queued`. Дальше коннектор без изменений. Воркер после песочницы для `kind = job` считает `acceptance_passed/total`, `regressions` против `baseline`, `solved`, статистику diff, статус попытки `evaluated`. `infra_error` переставляется один раз, как в квалификации.

## 4. HTTP API

Кабинет заказчика (cookie):
- `POST /jobs` (multipart: поля + `tests.zip`) → `draft`. `GET /jobs?mine=1`, `GET /jobs/{id}` (для заказчика — полная карточка с попытками), `PATCH /jobs/{id}` (только `draft | preflight_failed`), `POST /jobs/{id}/submit`, `POST /jobs/{id}/cancel`, `POST /jobs/{id}/accept {attempt_id}`, `POST /jobs/{id}/close`, `GET /jobs/{id}/attempts/{aid}/patch` (text/x-diff).
- `GET /jobs/quote?skill=go&bounty_cents=12000&attempts=3` → резерв, требуемый доступ, сколько агентов сейчас проходит по доступу.
- `GET /wallet` → балансы `available`, `reserved`, последние 50 проводок.

Кабинет владельца (cookie):
- `GET /work` → `{available: [...], locked: [{job, reason}], active: [...], history: [...]}`; `POST /jobs/{id}/take`.

Администратор (cookie + role admin): `GET /admin/jobs?status=pending_review`, `POST /admin/jobs/{id}/approve`, `POST /admin/jobs/{id}/reject {reason}`, `POST /admin/credits {email, amount_cents, note}`.

Коннектор: без новых эндпоинтов; `kind = job` в выдаче; `repo.tar.gz` отдаёт `jobs.repo_tar`.

## 5. Песочница

- Сборка образа заказа: сгенерированный Dockerfile (заказчик не пишет Dockerfile):
  - Go: `FROM arena-skill-go:1`, `COPY . /work`, `RUN go mod download` (если есть `go.mod`), тег `arena-job-{id}`.
  - Python: `FROM arena-skill-python:1`, `COPY . /work`, `RUN pip install --no-cache-dir -r requirements.txt` (если есть), `pip install --no-cache-dir -e .` (если есть `pyproject.toml` или `setup.py`).
  - `docker build --network default --memory 2g` с таймаутом 10 минут; размер образа сверх 2 GiB → `build_failed`.
- Прогоны: как в срезе 1, образ `image_tag`, без сети, копия репозитория с применённым diff и наложенными тестами.
- Удаление образа: при `accepted | closed_no_winner | cancelled`.

## 6. Кабинет

- Заказчик: `/hire` (список заказов со статусами и балансом), `/hire/new` (мастер: описание → репозиторий → тесты → бюджет и попытки с живой котировкой → отправить), `/hire/jobs/[id]` (статус; при `preflight_failed` — причина и базовая линия; при `open` — занятые слоты и прогресс; при `awaiting_acceptance` — сравнение: приёмочные x/y, регрессии, +/− строк, файлы, время, агент с рейтингом, «Принять», «Скачать патч», таймер автопринятия).
- Владелец: `/app/work` (вкладки «Доступно», «Заблокировано» с причиной вроде «Нужен доступ Go 1800, у вас 1650», «В работе», «История»), `/app/work/[jobId]` (описание, критерии, условия оплаты, «Взять»; после — статус попытки и итог).
- Администратор: `/admin` — заказы на модерации с описанием, репозиторием, базовой линией; начисление кредитов.
- Шапка: баланс кредитов, переключатель «Работа / Найм».

## 7. Тесты

- Модульные: разбор zip тестов (пути, лимиты, запрет `..` и абсолютных путей), снятие верхней папки и отбрасывание симлинков в тарболе, извлечение имён приёмочных тестов (Go и Python), вычисление «решено» и регрессий по базовой линии, потолок доступа (таблица точек Arena42), распределение выплат и резерва, порядок автопринятия.
- Интеграционные: импорт репозитория через подменяемый `RepoFetcher`; двойная запись (сумма по транзакции 0, баланс не уходит в минус); жизненный цикл заказа с fake runner и fake builder; `take` с каждой причиной отказа; конкурентный `take` на последний слот; автопринятие по `accept_by`; возврат резерва при каждом закрывающем пути.
- Docker: сборка образа для Go-репозитория с внешней зависимостью и прогон без сети; preflight на задаче, где приёмочный тест уже зелёный → `acceptance_already_passing`.
- e2e: заказчик → preflight → одобрение → два агента берут слоты → решения → сравнение → принятие → балансы.
- Приёмка: реальный публичный Go-репозиторий с настоящим багом, заказ на 3 попытки, живой агент.

## 8. Порядок

1. Книга кредитов и начисление администратором.
2. Импорт репозитория и тестов; модель заказа; черновик.
3. Сборка образа и preflight.
4. Модерация, открытие, доступ и потолок, `take`, попытки через коннектор.
5. Оценка попыток, закрытие приёма, принятие и автопринятие, расчёт.
6. API и контракт; e2e.
7. Кабинет заказчика, «Работа» владельца, админка.
8. Живая приёмка.

Критерий готовности: заказчик на реальном публичном репозитории публикует заказ на 3 попытки, два разных агента решают, заказчик видит сравнение, принимает одно, скачивает патч, и `git apply` проходит в его клоне; балансы в книге сходятся до цента.

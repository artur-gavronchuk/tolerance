# Срез 4: деньги и репутация

> **Отложено 25 сентября 2026.** Биржа (заказы, деньги, автопилот) снята с главного направления, см. раздел «Пересмотр 25 сентября» в `2026-09-23-platform-roadmap.md`. Спека сохранена как гипотеза и не исполняется.

24 сентября 2026. Строится поверх среза 3. Решения приняты автором по поручению владельца.

## 1. Что строим

Кредиты становятся деньгами. Заказчик пополняет баланс, резерв заказа и выплаты идут в долларах, платформа берёт комиссию, владелец агента выводит заработанное. Рядом с деньгами — репутация из реальной работы: принятые заказы влияют на рейтинг направления сильнее квалификации, в профиле появляются надёжность, число оплаченных заказов и заработок. Владелец видит P&L агента: выручка, комиссия, собственный compute.

**Момент продукта:** «FIXER-7 выполнил заказ. Вознаграждение +$120, compute −$7, комиссия −$12. Чистыми $101. Go 1842 → 1876.»

Вне среза: автоматические выплаты через провайдера (см. §2 «Провайдер»), налоговые документы, мультивалютность, споры.

## 2. Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Провайдер платежей | Интерфейс `payments.Provider` с первой реализацией `manual`: пополнение и выплата проводятся администратором вне платформы (банк, криптовалюта, что угодно) и фиксируются в книге с внешней ссылкой. Реализация `stripe` (Checkout для пополнений, Connect Express для выплат) проектируется здесь, но строится отдельным мини-срезом, когда выбрано юрлицо и юрисдикция | Stripe недоступен для части юрисдикций; маркетплейс с выплатам многим людям требует юрлица. `manual` позволяет брать реальные деньги у первых заказчиков уже сейчас, не блокируясь на этом решении |
| Валюта | `USD`, суммы в центах; книга из среза 3 получает вторую валюту. `CRD` остаётся для тестовых заказов и челленджей без приза | Не смешиваем тестовые кредиты и деньги |
| Какая валюта у заказа | Выбирает заказчик: `USD` или `CRD`; на `CRD` заказы идут только агенты, отметившие «принимаю тестовые заказы» (по умолчанию да) | Тестовые заказы не исчезают, но не выдаются за оплачиваемые |
| Комиссия | 10% от каждой выплаты агенту (и победителю, и финишёру), удерживается в момент расчёта на `platform:fees` | Простая модель, видна в каждой строке P&L |
| Минимум | Пополнение от $20; вывод от $20; заказ в `USD` от $20 bounty | Отсекает мелочь, где комиссия провайдера съедает смысл |
| Удержание | Выплата агенту уходит на `user:{uid}:pending` на 7 дней, затем на `available` | Окно на ошибки и отмену до того, как деньги можно вывести |
| Вывод | Владелец запрашивает вывод всего `available` в `USD` ≥ $20; администратор проводит вне платформы и отмечает с внешней ссылкой; до отметки сумма на `user:{uid}:payout_pending` | `manual`-провайдер; платёжных реквизитов платформа не хранит (администратор получает их вне системы) |
| Compute | Коннектор принимает стоимость, которую сообщает сам агент: файл `$ARENA_COST_FILE` (JSON `{"usd": 1.23}`), который команда агента может записать; для Claude Code — через `--output-format json` и `total_cost_usd`, пример в README. Значение self-reported, хранится на `proofs.agent_cost_cents`, показывается только владельцу и в его P&L | Честный учёт своих расходов нужен владельцу и автопилоту; заказчику и рейтингу он не нужен |
| Репутация в рейтинге | Каждая оценённая попытка заказа — прогон рейтинга с весом 2 и `score = acceptance_passed / acceptance_total`, минус 0.25 за каждую регрессию (не ниже 0); квалификационный прогон — вес 1. Неопределённость `350/√(сумма весов)` | Реальная работа весит вдвое больше синтетики и быстрее сужает ± |
| Надёжность | По направлению: доля «решено» среди последних 20 попыток заказов; показывается от 3 попыток | «47 оплаченных, 43 принятых, 96%» из концепции |
| Elite | Уровень `elite` открывается только при `access ≥ 2100` и ≥ 20 оценённых попытках заказов в направлении | Решение 2 roadmap и формула Arena42 (`trusted` + 20 jobs) |

## 3. Домен

- `ledger_accounts` получают `user:{uid}:pending`, `user:{uid}:payout_pending`, `platform:fees`, `system:deposits`, `system:payouts`; валюта — часть идентификатора счёта (`user:{uid}:available:USD`).
- `deposits`: `id`, `user_id`, `amount_cents`, `currency`, `provider`, `external_ref`, `status` (`recorded`), `recorded_by`, `created_at`.
- `payout_requests`: `id`, `user_id`, `amount_cents`, `currency`, `status` (`requested | paid | rejected`), `external_ref`, `reject_reason`, `created_at`, `processed_at`, `processed_by`.
- `jobs.currency`; `agents.accepts_test_jobs` (bool, true).
- `proofs.agent_cost_cents` (nullable).
- `skill_ratings` получают `weight_units` вместо `runs` в формуле (миграция переносит `runs → weight_units`), `job_attempts_count`, `job_solved_count`.
- `holds`: выплаты в удержании: `id`, `user_id`, `amount_cents`, `currency`, `release_at`, `released_at`, `ref`.

Расчёт заказа в `USD`: из `reserved` заказчика → победителю `bounty × 0.9` на `pending`, `bounty × 0.1` на `platform:fees`; финишёрам аналогично по 15%; остаток → `available` заказчика. Воркер раз в минуту переводит созревшие `holds` с `pending` на `available`.

## 4. HTTP API

- Владелец: `GET /earnings?period=30d` → выручка, комиссия, compute (self-reported), чистыми, по заказам; `POST /payouts` (вывод всего доступного), `GET /payouts`.
- Заказчик: `GET /wallet` с разбивкой по валютам; `POST /deposits/intent {amount_cents}` → инструкция для `manual` (реквизиты из конфигурации и код-ссылка) или URL Checkout для `stripe`.
- Администратор: `POST /admin/deposits {email, amount_cents, currency, external_ref}`, `GET /admin/payouts?status=requested`, `POST /admin/payouts/{id}/paid {external_ref}`, `POST /admin/payouts/{id}/reject {reason}`, `GET /admin/ledger/health` (сумма по всем проводкам = 0 по каждой валюте, нет отрицательных `available`).
- Публично: профиль агента дополняется `jobs_paid`, `jobs_accepted`, `reliability` по направлениям, `earned_total` (только если владелец включил показ — `agents.show_earnings`, по умолчанию выкл).

## 5. Кабинет

- `/app/earnings`: итоги за 7/30/90 дней и всё время, таблица по заказам (вознаграждение, комиссия, compute, чистыми), кнопка вывода, история выводов.
- `/app/work/[jobId]` после принятия: «+$120 · compute −$7 · комиссия −$12 · чистыми $101 · Go 1842 → 1876 · открыто 4 новых заказа».
- `/hire`: пополнение (для `manual` — инструкция и статус), валюта при создании заказа.
- `/admin`: пополнения, выводы, здоровье книги.

## 6. Тесты

- Модульные: распределение с комиссией до цента (округление: комиссия вниз, остаток агенту), `weight_units` в формуле рейтинга, надёжность по окну, гейт elite.
- Интеграционные: пополнение → заказ в USD → расчёт → удержание → созревание → вывод → отметка «выплачено»; книга сходится после каждого шага; вывод при недостатке средств; конкурентные выводы.
- e2e: полный денежный путь с `manual`-провайдером.
- Приёмка: реальное пополнение от реального заказчика на $20+, заказ, выплата владельцу вне платформы, отметка в админке.

## 7. Порядок

1. Книга: валюты, новые счета, удержания, проверка здоровья.
2. Провайдер `manual`: пополнения и выводы, админка.
3. Расчёт заказов в USD с комиссией; валюта заказа; флаг тестовых заказов.
4. Compute в коннекторе и P&L.
5. Репутация: веса в рейтинге, надёжность, гейт elite, профиль.
6. Кабинет: заработок, выводы, строка «чистыми»; контракт; e2e; приёмка.

## 8. Мини-срез 4b: Stripe (когда выбрано юрлицо)

Checkout Session на пополнение (webhook `checkout.session.completed` с проверкой подписи → проводка `system:deposits → available`), Connect Express для владельцев (онбординг по ссылке, `payouts_enabled` как условие вывода), Transfer на подключённый аккаунт при выводе, webhook `transfer.reversed` → откат. Идемпотентность по `event.id`. Реализация `stripe` рядом с `manual` за тем же интерфейсом; переключение конфигурацией `ARENA_PAYMENTS=stripe`.

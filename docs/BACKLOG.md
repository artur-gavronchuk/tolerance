# Бэклог для агента

Очередь работ по Studio после M1. Каждый пункт — один PR: агент берёт верхний незакрытый пункт, читает
`docs/SPEC.md` и `CLAUDE.md`, открывает PR и **не мержит его сам**. Мержит Артур после просмотра.

Как отдавать пункт агенту: «Возьми пункт N из `docs/BACKLOG.md`. Правила из CLAUDE.md в силе. Один PR,
в описании — что сделано, как проверить руками, что отложено».

## Что нужно по-настоящему

Studio держится на одном тезисе: **агент сдаёт работу, а система проверяет её против того, что утвердил
человек**. Всё остальное в спеке (два варианта плана, граф задач, параллельные агенты, Codex и OpenCode,
темы, провайдеры) — оболочка вокруг этой петли. Оболочка не доказывает, что петля кому-то нужна.

Поэтому сначала собирается **одна тонкая петля** на одной задаче и одном агенте:

> задача → критерии приёмки, которые утвердил человек → один implement-run в worktree →
> проверка: тесты, scope, вердикт по каждому критерию → diff и отчёт.

Петля считается собранной, когда Артур неделю пользуется ею на своём же репо (например, `tolerance-dev/arena`)
и видит ответ на вопрос: **ловит ли проверка задачи, которые агент объявил сделанными, а они не сделаны?**
Если ловит регулярно, это и есть продукт, остальное — вторично. Если не ловит, расширять оболочку рано.

Пока петля не собрана и не опробована: никаких новых экранов, тем, графов и агентов.

## Правила очереди

- Один пункт — один PR. Не больше одного PR в работе на пункт, без «заодно поправил дизайн».
- PR готов, когда `pnpm check` зелёный и в описании есть шаги ручной проверки.
- Изменения ядра (`packages/engine`, `packages/git`, `packages/agents`) Артур читает сам перед мержем.
- Решения вне спеки — строкой в `docs/DECISIONS.md`. Итог майлстоуна — в `docs/milestones/`.
- Редизайн, новые темы и экраны вне списка — только по отдельной просьбе.

## Очередь: тонкая петля

### 1. Задача → план с критериями приёмки — сделано (PR #5)

Два варианта плана с задачами, scope и критериями; один утверждается. Для петли достаточно, что у
утверждённого варианта есть задачи с критериями. Второй вариант и редактор плана не нужны, пока петля не
опробована.

### 2. Одна задача в worktree (M2, SPEC §3.4) — сделано

`packages/git`: worktree в `~/.studio/worktrees/<project>/<plan>/<task>`, ветка `studio/*`, guard на удаление
(только внутри корня после realpath), коммит за агента, diff от merge-base с untracked. Implement-run:
Claude Code с правом правки только внутри worktree, команды из allowlist проекта, без bypass-permissions,
промпт из задачи (описание, scope, критерии). Diff по задаче в UI (сначала простой текстовый, Monaco потом).
Задачи утверждённого плана выполняются **по одной, кнопкой**: без scheduler и параллелизма.
_Готово, когда:_ задача утверждённого плана делается в worktree, diff виден, основная ветка не тронута.

### 3. Проверка результата против плана (M5, SPEC §3.5 п.6) — ядро

(a) `testCommand` проекта в worktree задачи; (b) scope-check без LLM: файлы diff против glob задачи;
(c) verify-run только на чтение, по умолчанию другой моделью, чем исполнитель: вердикт pass / fail / unclear
по каждому критерию со ссылками file:line, плюс незапланированные изменения. Критерий `check: 'command'`
выполняется скриптом, а не оценивается моделью. Отчёт под задачей: что прошло, что нет, с цитатами.
_Готово, когда:_ по задаче из п.2 есть отчёт, и в нём видно, что агент сделал, а что только заявил.

### 4. Пробный пробег и честный итог

Не код. Артур неделю гоняет петлю на `tolerance-dev/arena`: 5–10 реальных задач. Фиксирует в
`docs/milestones/LOOP.md`: сколько задач, сколько раз проверка поймала незавершённое, сколько ложных
срабатываний, что мешало. По итогу решается, что из оболочки нужно первым.

## Ежедневный режим (замена Superset)

Фундамент петли, идёт параллельно с ней: Артур работает в Studio каждый день вместо Superset — воркспейс
(ветка + worktree), Claude Code в терминале, статусы, diff, коммит, PR. Те же worktree и diff, что у петли,
только вход другой. Петлю (пункты 2–4) не трогает. Критерий минимальности: без этого Артур вернётся в Superset.
Исследование — `docs/research/daily-driver.md`; его раздел «Предлагаю изменить» принят и уже учтён ниже. Итог — `docs/milestones/DAILY.md`.

### D1. Воркспейс = ветка + worktree

«Новый воркспейс»: имя → ветка `studio/ws/<slug>` от свежей `origin/<основная>` (fetch одной ветки; без сети —
от локальной), worktree в
`~/.studio/worktrees/<project>/ws/<slug>` (`packages/git` из PR #6). После создания — `setupCommand` проекта
в worktree, вывод виден в UI. Слева список воркспейсов с веткой и временем. Удаление: предупреждение о
незакоммиченном, затем guard; ветка остаётся. «Открыть в терминале» (команда настраивается), «Открыть в
редакторе» (`code`, `cursor`, `idea`), «Открыть папку». Блок настроек в экране проекта: setup, команда агента
(по умолчанию `claude`), редактор, терминал.
_Готово, когда:_ Артур создаёт 2–3 воркспейса и работает в них из внешнего терминала.

### D2. Встроенный терминал с агентом

node-pty в main, xterm.js (fit, search, web-links; без webgl) в renderer. Вкладки терминалов в воркспейсе: первая запускает агента проекта
(`claude --session-id <uuid>`, uuid генерирует Studio и хранит в SQLite; команда настраивается), вторая —
shell. Агент в своём TUI, без ACP-чата. Переключение воркспейсов не убивает процессы и не теряет вывод
(буфер в main), resize корректный. Нативный модуль — строка в DECISIONS.
_Готово, когда:_ рабочий день проходит во встроенном терминале, внешний не нужен.

### D3. Статусы агентов и уведомления

`working` / `needs_input` / `idle` / `exited` из хуков Claude Code, не из вывода терминала: `UserPromptSubmit`,
`PostToolUse` → working; `PermissionRequest`, Notification по `notification_type` → needs_input; `Stop` → idle.
Последний `session_id` из хуков сохраняется (он меняется после `/clear` и `/resume`). Хуки — `type: "http"` через
`claude --settings <файл в ~/.studio/>` на локальный HTTP-сервер в main с токеном воркспейса из env;
глобальный конфиг не трогается. Точка статуса у воркспейса, счётчик «ждут меня», ОС-уведомление на
`needs_input` и `idle`, клик открывает воркспейс. Без хуков — `exited` по выходу и watchdog по тишине
(SPEC §3.3). Тест — фейковый агент-скрипт в pty, дёргающий хук-эндпоинт по сценарию.
_Готово, когда:_ ведя три воркспейса, Артур идёт туда, где горит «ждёт», а не заглядывает в каждый.

### D4. Изменения → коммит → PR, перезапуск

Вкладка «Изменения»: файлы и текстовый diff от merge-base с основной веткой, с untracked. «Коммит»
(сообщение пишет Артур), «Push», «Создать PR» через `gh`, без него — показать команды. В основную ветку Studio
не мержит. Воркспейсы и сессии переживают перезапуск: список из SQLite, агент продолжается
`claude --resume <последний session-id>`; если сессии нет — свежий старт с новым id.
_Готово, когда:_ от «новый воркспейс» до открытого PR — не выходя из Studio, и перезапуск ничего не ломает.

### D5. Сбор болей

Кнопка и горячая клавиша «Боль» везде: строка → `~/.studio/pains.md` с датой, проектом и воркспейсом.
`docs/milestones/DAILY.md`: что сделано, что отложено, как проверить руками.
_Готово, когда:_ боль записывается за секунды, не уходя из воркспейса, и файл можно отдать агенту.

**Не делать в основе:** браузер-превью и порты, design-режим, облако и аккаунты, мобильное, сетку панелей,
командную палитру, свой чат поверх ACP, Windows, новые темы и редизайн, запуск нескольких агентов одной
кнопкой. Если без чего-то нельзя работать — в «Кандидаты по болям» в `docs/research/daily-driver.md`.

_Режим готов, когда:_ Артур целый рабочий день на `tolerance-dev/arena` ведёт 2–3 задачи параллельно в Studio
и ни разу не открывает Superset.

## Потом, только после пробега

- Follow-up из ревью: комментарии к diff → новая сессия агента → повторная проверка.
- Несколько задач плана подряд: интеграционная ветка, merge по готовности, конфликты. Параллелизм — ещё позже.
- Редактор плана и граф задач; граф карты с подсветкой затронутых компонентов.
- Второй агент через ACP (Codex или OpenCode), чтобы верификатор был из другого семейства, чем исполнитель.
- Быстрый режим для мелких задач: один вариант и сразу исполнение.
- Распространение изменений: правка критерия в утверждённом плане показывает, что стало недействительным.
- Онбординг, провайдеры OpenCode, прокси, сборка `.dmg` / `.AppImage`.

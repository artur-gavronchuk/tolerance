# Как устроен агент: пишем свой за час и натравливаем на танки

Слово «агент» в последний год обросло смыслами настолько, что им называют
и чат с системным промптом, и продукт, который сам открывает пул-реквесты.
Разница между ними не в маркетинге, а в одной конкретной вещи: агент — это
модель, которой дали инструменты и разрешили звать их в цикле, пока она
не решит, что закончила. Всё остальное — детали реализации.

В этом тексте я соберу такого агента с нуля, на голом Claude API, без
фреймворков — получится около 150 строк. Потом натравлю его на реальную
задачу: заставлю написать бота для танкового тира на
[tolerance](https://tolerance.cc) — арене, где боты сражаются в постоянном
турнире и это можно смотреть вживую. Весь код есть в репозитории,
`examples/mini-agent/`.

## 1. Чем агент отличается от чата

В обычном чате модель отвечает на сообщение текстом. Один запрос — один
ответ. Она не может ничего проверить: если попросить её написать функцию,
она напишет то, что кажется правильным по её внутренней модели языка, и на
этом всё — ни разу не запустив код, она не узнает, ошиблась она или нет.

Агент — это тот же вызов API, но с двумя добавками:

1. **Инструменты.** Модели дают список функций с описаниями и схемами
   аргументов (`tools` в запросе). Вместо текстового ответа она может
   вернуть `tool_use` — «вызови функцию `read_file` с аргументом
   `path="bot.py"`». Код на вашей стороне эту функцию реально выполняет и
   отдаёт результат обратно.
2. **Цикл.** Ответ с результатом инструмента снова уходит модели, она
   решает, что делать дальше — позвать ещё один инструмент или закончить
   ход, — и так пока не сочтёт задачу выполненной (`stop_reason ==
   "end_turn"`) или пока не кончится лимит шагов.

Ничего сверхъестественного в этом нет: `POST /v1/messages` как был одним
эндпойнтом, так и остался. Просто теперь модель не отвечает вам напрямую,
а по дороге может почитать файлы, что-то поправить и прогнать тесты — и
только потом сказать, что сделала.

## 2. Минимальный агент

Возьмём Anthropic SDK для Python и напишем цикл руками — без
`tool_runner` из SDK (он ещё в бете и прячет часть деталей, а мне хочется
их показать) и без готовых агентных фреймворков. Модель по умолчанию —
`claude-sonnet-5`, с возможностью переопределить через `AGENT_MODEL`
(полезно, если захочется прогнать то же самое на другой модели и сравнить).

### 2.1 Инструменты

Инструментов четыре, и все они работают с файлами и командами внутри
одного рабочего каталога:

```python
def tool_list_files(path: str = ".") -> str: ...
def tool_read_file(path: str) -> str: ...
def tool_write_file(path: str, content: str) -> str: ...
def tool_run(command: str, timeout_s: int = 30) -> str: ...
```

Каждый описан для модели как обычная функция с JSON-схемой аргументов:

```python
{
    "name": "write_file",
    "description": "Write (overwrite) a text file, creating parent directories if needed.",
    "input_schema": {
        "type": "object",
        "properties": {
            "path": {"type": "string", "description": "Path relative to the working directory."},
            "content": {"type": "string", "description": "Full new contents of the file."},
        },
        "required": ["path", "content"],
    },
}
```

Модель не выполняет код сама — она только формирует такие вызовы. Выполнять
их обязан ваш код, и здесь прячется единственная по-настоящему важная
часть всего примера: **что вы позволите агенту сделать с диском и
процессом**.

### 2.2 Рабочий каталог — единственная граница

Агент работает там, откуда его запустили (`Path.cwd()`), и не должен
выйти за пределы этой папки ни при чтении, ни при записи. Проверка одна и
используется во всех четырёх инструментах:

```python
def safe_path(rel: str) -> Path:
    """Resolve rel against the working directory and reject anything that
    escapes it, including via a symlink (resolve() follows symlinks, so a
    link pointing outside is caught by the containment check below)."""
    candidate = (WORK_DIR / rel).resolve()
    if candidate != WORK_DIR and WORK_DIR not in candidate.parents:
        raise ValueError(f"path escapes the working directory: {rel}")
    return candidate
```

Важная деталь: `Path.resolve()` разворачивает симлинки. Значит, если модель
попросит записать файл по пути `some_dir/link_outside/pwned.txt`, а
`link_outside` окажется симлинком на `/etc`, `resolve()` вернёт реальный
путь снаружи рабочего каталога — и проверка `WORK_DIR not in
candidate.parents` его отловит. Если проверять пути строкой
(`"../" in path`), это легко обойти; резолвить путь и сравнивать
результат — нет.

Обычная ошибка здесь — понадеяться на то, что модель «не будет» просить
`../../.ssh/id_rsa` или `/etc/passwd`, потому что «зачем ей». Модель ничего
не хочет в человеческом смысле — она максимизирует правдоподобие следующего
токена по инструкции, которую вы ей дали, и инструкция может быть
неудачной, двусмысленной или (в проде) вообще не вашей — если агент читает
чужой текст (issue, страницу, вывод команды) и в нём есть текст, похожий на
инструкцию. Граница должна держаться не потому, что модель хорошая, а
потому, что код её не пропустит.

### 2.3 Таймаут и лимит вывода для команд

`run` — самый опасный инструмент из четырёх, потому что он не файл читает,
а исполняет что угодно через `sh -c`. Два ограничения обязательны:

```python
def tool_run(command: str, timeout_s: int = 30) -> str:
    timeout_s = max(1, min(int(timeout_s), MAX_RUN_TIMEOUT_S))  # MAX_RUN_TIMEOUT_S = 120
    try:
        proc = subprocess.run(
            command, shell=True, cwd=WORK_DIR,
            capture_output=True, text=True, timeout=timeout_s,
        )
    except subprocess.TimeoutExpired:
        return f"error: command timed out after {timeout_s}s"
    output = cap_output((proc.stdout or "") + (proc.stderr or ""))
    return f"exit code: {proc.returncode}\n{output}"
```

Таймаут капается на 120 секунд вне зависимости от того, что попросила
модель — иначе `run("sleep 999999")` подвесит весь цикл. Вывод капается на
8 KiB — без этого один неудачный `find /` или бесконечный принтф в цикле
разгонит счёт за токены на порядок, потому что весь этот вывод улетит
обратно в модель как результат инструмента и будет пересчитываться в
каждом следующем запросе (API не хранит состояние — история отправляется
целиком на каждый шаг).

### 2.4 Сам цикл

```python
messages = [{"role": "user", "content": task}]

for step in range(1, MAX_STEPS + 1):  # MAX_STEPS = 40
    response = client.messages.create(
        model=MODEL, max_tokens=4096,
        system=SYSTEM_PROMPT, tools=TOOLS, messages=messages,
    )
    messages.append({"role": "assistant", "content": response.content})

    if response.stop_reason != "tool_use":
        for block in response.content:
            if block.type == "text":
                print(block.text)
        return  # end_turn (или что-то ещё, что не tool_use) — агент закончил

    tool_results = []
    for block in response.content:
        if block.type != "tool_use":
            continue
        print(f"[step {step}] {block.name}({json.dumps(block.input)})")
        try:
            result = HANDLERS[block.name](**block.input)
            is_error = False
        except Exception as e:
            result, is_error = f"error: {e}", True
        tool_results.append({
            "type": "tool_result", "tool_use_id": block.id,
            "content": str(result), "is_error": is_error,
        })
    messages.append({"role": "user", "content": tool_results})
```

Три вещи здесь заслуживают внимания:

- **История растёт, а не заменяется.** Каждый шаг дописывает в `messages`
  ход ассистента и результаты инструментов — API не помнит ничего между
  вызовами, весь контекст едет туда-сюда целиком.
- **Ошибка инструмента — это `tool_result` с `is_error: true`, а не
  исключение, которое роняет цикл.** Модель должна увидеть, что путь
  отклонён или команда упала, и это часть протокола, а не авария.
  40 строк кода не пытаются угадать, что было не так, — они просто
  показывают модели ровно то, что случилось.
- **Лимит шагов — это не оптимизация, а защита.** Без него агент, который
  зациклился (пишет файл, читает его же, снова пишет то же самое), будет
  жечь токены бесконечно. 40 шагов — щедрый лимит для маленькой задачи;
  если он упирается в потолок, это сигнал, что задача либо
  сформулирована плохо, либо агенту не хватает инструментов, а не повод
  просто поднять число.

Импорт `anthropic` в примере намеренно спрятан внутрь `main()` — так
`agent.py` можно импортировать и тестировать функции инструментов
(`test_tools.py`, без сети и без API-ключа) даже там, где пакет `anthropic`
не установлен.

## 3. Обратная связь — вот что на самом деле важно

Всё вышеописанное — это водопровод: как дать модели дотянуться до файлов
и команды. Отдельный вопрос — зачем ей это. Ответ в том, что агент без
способа проверить собственную работу ничем не отличается от чата: он
пишет код, который выглядит правильным, и на этом останавливается,
потому что у него нет способа узнать, что это не так.

Разница между «агент написал что-то похожее на решение» и «агент решил
задачу» — это обратная связь, которую он может получить сам, без человека
в цикле:

- **Тесты.** Если в проекте есть `pytest` или `go test`, у агента есть
  тривиальный способ проверить себя: `run("pytest -q")` — и результат
  либо подтверждает правку, либо тут же показывает, что сломалось.
- **Линтер и компилятор.** Дешевле теста: синтаксическая ошибка или
  опечатка в имени переменной ловится за секунды, а не за 40 шагов
  блуждания.
- **Сама программа.** Не у каждой задачи есть тесты. У ботов для танков
  их нет — зато есть матч: `arena tanks play . house:hunter --seed 1`
  за пару секунд честно покажет, выигрывает бот или проигрывает.

Без этого агент — это генератор одной попытки, у которого просто более
длинный system-промпт, чем у чата. С этим — цикл «правка → прогон →
чтение результата → следующая правка» превращается в то, что реально
похоже на работу разработчика, только быстрее и без перерывов на кофе.
Собственно, это и есть главная причина писать тестируемый, легко
прогоняемый код, если у вас есть агенты в разработке: не «для людей
удобнее», а «агент сам себя может проверить только если ему есть на чём».

## 4. Практика: агент пишет бота для танков

### 4.1 Правила в двух абзацах

Матч в tolerance — до четырёх танков на поле 60×40 юнитов, без тумана
войны: каждый видит всех. Тик — десять раз в секунду, матч идёт до 1200
тиков (две минуты) или пока не останется максимум один живой танк. Танк —
круг радиусом 1.0, едет вперёд со скоростью 5 юнитов/с, назад — 3,
корпус поворачивается на 2.5 рад/с, башня отдельно от корпуса — на
4 рад/с. Инерции нет: скорость на этом тике — это `move × максимум`, не
сила.

Перезарядка — 10 тиков, снаряд вылетает из точки в 1.3 юнита от центра
танка и летит со скоростью 24 юнита/с, живёт 30 тиков, наносит 25 урона
при 100 максимума HP. Аптечка лечит на 35 HP (не выше максимума) и
появляется заново через 150 тиков после того, как её взяли. С 800-го
тика начинает сжиматься зона — от радиуса, покрывающего всё поле (37), до
радиуса 6 к 1100-му тику, дальше не меняется; вне зоны танк теряет 1 HP
за тик. Места после матча: живые выше мёртвых, среди живых — больше HP,
затем больше урона; среди мёртвых — кто умер позже, затем больше урона.

### 4.2 Протокол — процесс и JSON-строки

Бот — обычный процесс. Платформа один раз присылает ему `start` с
правилами, стенами и списком игроков и ждёт `ready` в течение 5 секунд.
Дальше на каждый тик приходит `tick` с позициями всех танков, снарядов,
аптечек и зоны, и от бота ждут ответ с тем же номером тика:

```json
→ {"type":"tick","tick":17,
   "tanks":[{"id":0,"x":12.3,"y":8.1,"hull":0.52,"turret":0.9,"hp":75,"reload":3,"alive":true}],
   "shells":[{"id":41,"owner":1,"x":20.0,"y":14.2,"vx":-24.0,"vy":0.0}],
   "bonuses":[{"x":30.0,"y":24.0}],
   "zone":{"x":30,"y":20,"r":37}}
← {"tick":17,"move":1,"turn":0,"turret":-0.5,"fire":true}
```

`move`, `turn`, `turret` — в диапазоне [-1, 1], `fire: true` стреляет,
если перезарядка на этом тике равна нулю. На ответ даётся 200 мс; первые
20 мс раздумий на тик бесплатны, всё, что сверху, списывается с общего
бюджета в 20 секунд на весь матч — кончится бюджет, бот отключат до конца
матча со статусом `timeout`. После конца матча приходит `end` с итоговыми
местами, и на этом процесс должен завершиться.

### 4.3 Стартовый бот

`arena tanks new` выдаёт рабочую заготовку — `bot.json`, `bot.py` и
`tanks.py` с геометрией (углы, расстояния, поиск ближайшего врага,
упреждение цели) и циклом чтения протокола. Сама стратегия в `bot.py` —
«охотник»: едет к ближайшему живому врагу и стреляет, когда навёл башню:

```python
class Hunter:
    def decide(self, msg):
        me = next(t for t in msg["tanks"] if t["id"] == self.me_id)
        target = tanks.nearest_enemy(me, msg["tanks"])
        target_angle = tanks.angle_to(me["x"], me["y"], target["x"], target["y"])
        hull_diff = tanks.angle_diff(target_angle, me["hull"])
        turn = max(-1.0, min(1.0, 3 * hull_diff))
        dist = tanks.distance(me["x"], me["y"], target["x"], target["y"])
        move = 1.0 if dist > 6 else 0.0
        turret_diff = tanks.angle_diff(target_angle, me["turret"])
        turret = max(-1.0, min(1.0, 4 * turret_diff))
        fire = abs(turret_diff) < 0.08
        return {"move": move, "turn": turn, "turret": turret, "fire": fire}
```

Из встроенных домашних ботов на сервере (они написаны на Go и живут прямо
в процессе движка, без отдельного протокола) есть `hunter` — примерно то
же самое поведение, и `sniper` — держит дистанцию, стреляет с
упреждением, уходит от летящих снарядов и идёт к аптечке на низком HP.
Против `sniper` голый `hunter` из заготовки обычно проигрывает: он не
уклоняется и не ведёт цель.

Вот реальный прогон заготовки без единой правки — `arena tanks play`
играет локально, тем же движком, что и сервер:

```
$ arena tanks new mybot
Wrote a python starter bot to mybot
$ arena tanks play mybot house:hunter house:sniper --seed 1
Seed: 1 (reproduce with --seed 1)
place  name          kills  damage  status  answered
1      house:sniper  2      200     ok      157
2      my-tank       0      0       ok      157
3      house:hunter  0      50      ok      47
Replay: tanks-replay.json — open it at https://tolerance.cc/tanks/replay
```

Заготовка не набрала ни одного попадания за весь матч — она честно
доезжает до противника и стреляет, но не целится по факту движения цели и
не уклоняется от снарядов `sniper`. Это и есть задача, которую я отдал
агенту: `AGENT_TASK.md` в реальном прогоне агента для написания бота в
tolerance звучит так —

> You are improving a bot for the tolerance tanks game. The rules and the
> protocol are in GAME.md; your bot's recent results are in RESULTS.md.
> Edit the bot in place (keep bot.json valid; standard library only). Test
> it locally before you finish: `arena tanks play . house:hunter
> house:sniper --seed 1`, repeat with other seeds; aim to place first more
> often than the house bots. Do not edit GAME.md or RESULTS.md; they are
> not part of the bot. You have 20 minutes.

Ровно так работает и кнопка «Let my agent write the bot» в кабинете
tolerance: платформа готовит папку с текущей версией бота (или заготовкой,
если версии ещё нет), кладёт туда `GAME.md` и `RESULTS.md` (историю
последних матчей бота) и запускает `agent.command` из
`~/.arena/config.yaml` без аргументов — агент читает задание из
`TASK.md`, ровно как `mini-agent` умеет делать при вызове без аргумента
командной строки.

## 5. Ошибки, на которых спотыкаются агенты

Несколько вещей ломают ботов настолько предсказуемо, что стоит
перечислить их отдельно — и агент, и человек наступают на одни и те же
грабли.

**stdout вместо stderr.** Оставленный `print("thinking...")` перед
JSON-ответом — самая частая ошибка. Протокол читает stdout построчно и
ждёт JSON-объект с числовым `tick`; строка, которая под это не подходит,
просто игнорируется — но считается. Ход всё равно засчитывается, если
настоящий ответ пришёл вовремя следующей строкой, так что один случайный
`print` матч не ломает. Ломает накопление: больше 1000 таких посторонних
строк за матч — и бот отключают до конца со статусом `invalid`. Правильное
место для отладочного вывода — stderr (в `tanks.py` для этого есть
`log()`), его платформа хранит отдельно и показывает только владельцу
бота.

**Буферизация stdout.** Питоновский `print` по умолчанию не сбрасывает
буфер построчно, когда стоит не в терминал, а в пайп — а именно так его
и запускает платформа. Без `-u` (`python3 -u <entry>`, ровно так
платформа и запускает питоновские боты) или явного `flush=True` в каждом
`print` ответы могут копиться в буфере и приходить с опозданием одной
пачкой — а к этому моменту тики, на которые они формально отвечали, уже
пропущены по таймауту.

**Выход за время тика.** 200 мс на тик — это не «в среднем», а жёсткий
дедлайн на каждый конкретный ответ; опоздавший на один тик ответ просто
пропускается, танк на этом тике стоит на месте. Опаснее общий бюджет:
первые 20 мс раздумий на тик бесплатны, но всё, что дольше, тратит общий
резерв в 20 секунд на весь матч — а это довольно легко выесть, если бот
на каждом тике пересчитывает что-то тяжёлое (например, честно перебирает
траектории всех снарядов вместо аналитического решения, как в
`lead_target`). Кончится бюджет — бот отключат до конца матча.

**Упреждение.** Стрелять точно в текущие координаты цели — способ
никогда не попадать по движущемуся танку: пока снаряд летит 24 юнита в
секунду, цель успевает сместиться. Готовая `lead_target` в `tanks.py`
решает квадратное уравнение на точку встречи снаряда и цели — но её всё
равно нужно осознанно вызвать с правильной скоростью цели, которую
нужно оценить по разнице позиций между двумя последними тиками (в
`tick`-сообщении скорость не приходит напрямую).

## 6. Попробуйте сами

Всё, что описано выше, можно прогнать не отходя от терминала — регистрация
на [tolerance](https://tolerance.cc) бесплатная и с готовой формой входа.

1. Зарегистрируйтесь, создайте агента и API-ключ в кабинете.
2. Скачайте коннектор и подключитесь: `arena login`, `arena init`, впишите
   команду запуска своего агента в `~/.arena/config.yaml` (например,
   `python3 /path/to/mini-agent/agent.py`, если взяли пример из этой
   статьи), затем `arena connect` — коннектор держит связь с платформой,
   пока работает.
3. В кабинете, на странице Tanks, нажмите «Let my agent write the bot».
   Платформа соберёт папку с текущей версией бота (или заготовкой, если
   версии ещё нет), правилами и историей матчей и запустит вашего агента.
4. Готовую версию платформа сама прогонит через проверку (пакет
   разбирается, бот отвечает `ready`, выдерживает пробный матч против
   `house:idle` и обыгрывает его) и, если всё прошло, поставит в турнир с
   пометкой «written by agent».

Ручная загрузка бота (`arena tanks submit` или архив в кабинете) работает
точно так же и проходит те же проверки — просто в таблице турнира у
такого бота не будет пометки «agent», а у ботов, написанных подключённым
агентом, будет. Разница видна сразу, без доверия на слово.

Дальше — эфир: `/tanks` показывает текущий матч в реальном темпе, таблицу
рейтинга и последние результаты, а у каждого матча есть страница с
повтором в 2D и 3D и ссылкой, которой можно поделиться. Смотреть можно
без входа: https://tolerance.cc/tanks

## 7. Что дальше

Танковая арена — это витрина, которая уже сейчас честно показывает,
работает ли чей-то агент сам по себе: результат матча нельзя подделать
текстом. Дальше платформа растёт в ту же сторону — доказательства вместо
слов:

- **Квалификация по направлениям.** Не один результат «прошёл / не
  прошёл», а рейтинг по конкретным направлениям (например, «чинить баги
  на Go», «чинить баги на Python») на прогоне из нескольких скрытых
  задач подряд.
- **Рейтинг агентов с честной неопределённостью.** Новый агент или новая
  версия старого начинает с широкого доверительного интервала, который
  сужается по мере накопления результатов — так же, как рейтинг ботов в
  танках уже считается сейчас (Weng–Lin, тот же принцип, что у
  TrueSkill/OpenSkill).
- **Соревнования.** Челленджи на инженерных задачах с дедлайном и
  таблицей мест, и игровые сезоны сверх непрерывного ладдера — оба
  поверх той же механики «прогон → оценка», которая уже используется в
  проверках и в турнире ботов.

Ничего из этого не про заказы или заработок — платформа сейчас
целенаправленно не в эту сторону: сложность формулирования задачи, доверие
к чужому коду и доступ к приватным репозиториям делают биржу отдельной,
отложенной темой. В центре остаётся вопрос попроще и одновременно
интереснее: как по-честному показать, что агент умеет работать сам — а не
рассказать об этом.

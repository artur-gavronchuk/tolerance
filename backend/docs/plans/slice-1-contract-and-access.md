# План среза 1: контракт и доступ

Версия 0.1 · 17 сентября 2026. Конкретизирует срез 1 из
[implementation-plan.md](../implementation-plan.md) до списка задач. Источник
решений — [backend-design.md](../backend-design.md); при расхождении этот план
уточняет порядок, не отменяет решения дизайна.

## Цель среза

Владелец публикует контракт миссии через API; чужая организация не читает
закрытые данные по id; опубликованная версия миссии не редактируется. Без
сдачи, оценки, исполнения агентов — это срез 2 и далее.

## Объём

**Входит:**

- `internal/platform/db` — pgx-пул, обёртка транзакции с `SET LOCAL app.organization_id`.
- `internal/platform/auth` — проверка JWT access-токена по JWKS (без полного
  discovery-флоу; issuer и JWKS URL задаются конфигурацией).
- `internal/platform/httpx` — problem-ответы, request id, декодер с
  `DisallowUnknownFields`, обёртка идемпотентных команд.
- `internal/platform/audit` — запись события в текущей транзакции.
- `internal/identity` — `organizations`, `users`, `memberships`; middleware
  аутентификации, резолвинг `Actor` из токена и заголовка `X-Organization-Id`.
- `internal/campaigns` — создание, чтение, список, переходы `activate` /
  `complete` / `cancel`.
- `internal/missions` — создание миссии с первой версией контракта
  (`draft`/`calibrating`), `POST /missions/{id}/open` с расчётом
  `contract_digest` и заморозкой версии, чтение.
- `internal/budget` — лимит кампании: создать/получить; резервы и списания —
  срез 2 (сдача) и срез 4 (управляемое исполнение).
- Миграции (`migrations/`, goose) для перечисленных таблиц плюс
  `audit_events`, `idempotency_records`, `jobs` (пустая, задел под срез 2).
- RLS на всех tenant-таблицах, роль `forge_app` без `BYPASSRLS`.
- `contracts/openapi/openapi.yaml` — маршруты этого среза.
- `docker-compose.yml` — PostgreSQL для разработки.
- `cmd/api/main.go` — сборка зависимостей, запуск HTTP-сервера.

**Не входит:** artifacts, submissions, evaluation, acceptance, execution,
usersessions, publication, SSE. Полный OIDC-провайдер в compose (Dex) — по
решению не входит в этот срез; проверка токена реализуется по-настоящему
(JWKS, подпись, `iss`/`aud`/`exp`), но интеграционные тесты используют
локальный тестовый JWKS-сервер вместо поднятия Dex. Реальный провайдер
подключается перед внешним пилотом, конфигурацией, без изменений кода.

## Задачи по порядку

1. **Платформенные пакеты без БД**: `idgen` (сделано), `httpx.Problem` и коды
   ошибок, `auth.Verifier` с тестовым JWKS. Модульные тесты, без сети и БД.
2. **Схема и миграции**: таблицы identity, campaigns, missions,
   mission_versions, requirements, budgets, audit_events,
   idempotency_records, jobs. Триггер неизменяемости опубликованной версии.
   RLS-политики. Тест на testcontainers: миграция применяется чисто,
   миграция идемпотентна повторно.
3. **`db.Tx`**: транзакция с `SET LOCAL app.organization_id`; без актора
   транзакция не открывается. Тест: запрос без установки видит ноль строк
   чужой организации даже при ошибке в фильтре WHERE (RLS как барьер).
4. **identity**: upsert пользователя по `(issuer, subject)`, проверка
   членства, middleware. Тест: неизвестный токен → 401; известный токен без
   активного членства в организации из заголовка → 403.
5. **campaigns**: сервис + HTTP. Тест: создание, получение своей кампании,
   404 на кампанию другой организации, `409` при переходе из недопустимого
   состояния.
6. **missions**: создание версии, `open` с расчётом `contract_digest`,
   заморозка. Полная калибровка по сценариям (`scenario_bundles`,
   `calibrations`) невозможна без оценщика и переносится в срез 2 вместе с
   ним; в этом срезе `calibrating → open` требует явного подтверждения
   организатором (`mission_versions.calibration_confirmed_at`) — заглушка,
   которую срез 2 заменит настоящей проверкой по сценариям, не убирая сам
   гейт. Тест: повторный `UPDATE` опубликованной версии отклоняется на
   уровне БД (триггер) и на уровне API; `open` без подтверждённой
   калибровки — `409`; два параллельных `open` с устаревшей версией — один
   `409 state_conflict` (оптимистическая блокировка).
7. **budget**: лимит кампании, создание, чтение. Без резервов.
8. **Идемпотентность**: обёртка `command()` из прототипа, перенесённая на
   Postgres-таблицу вместо JSON-файла. Тест: два одинаковых `POST` с одним
   `Idempotency-Key` — один результат; тот же ключ с другим телом — `409`.
9. **OpenAPI**: описать маршруты этого среза, добавить проверку ответов
   сервера по схеме в тестах хендлеров.
10. **compose и `cmd/api`**: собрать зависимости, поднять сервер, ручная
    проверка полного цикла curl'ом.

## Критерии готовности (проверяются тестами, не только вручную)

Статус: реализовано, все пункты покрыты автоматическими тестами (см.
`cmd/api/main_test.go` для сквозного сценария и integration-тесты каждого
модуля для остального). `go test ./...` требует Docker (testcontainers-go);
без Docker интеграционные тесты пропускаются (`t.Skip`), а не падают.

- [x] `go test ./...` зелёный, включая интеграционные с testcontainers.
- [x] Владелец публикует контракт: `POST /organizations` → `POST /campaigns`
      → `POST /campaigns/{id}/missions` (создаёт черновик с первой версией
      контракта; отдельного `POST /missions/{id}/versions` в этом срезе нет,
      см. «Явно отложено») → `POST /missions/{id}/confirm-calibration` →
      `POST /missions/{id}/open` возвращает `contract_digest`.
      Проверено сквозным тестом `cmd/api.TestEndToEnd_OwnerPublishesContractAndItStaysIsolatedAndImmutable`.
- [x] Чужая организация получает `404` на `GET /missions/{id}` и
      `GET /campaigns/{id}` по точному известному id (наличие объекта не
      раскрывается); отдельно — актор без активного членства в
      организации, указанной в `X-Organization-Id`, получает `403` ещё до
      обращения к какому-либо объекту (`internal/identity` middleware-тесты).
- [x] `UPDATE requirements` или `mission_versions` опубликованной версии
      напрямую в БД (в тесте, с ролью-владельцем схемы) отклоняется
      триггером (`internal/platform/db` integration-тесты).
- [x] Два конкурентных `POST /campaigns/{id}/activate` и
      `POST /missions/{id}/open` с одинаковой ожидаемой версией: ровно один
      успешен, второй получает `409` (`internal/campaigns`,
      `internal/missions` integration-тесты).
- [x] Повтор идемпотентной команды с тем же ключом и телом не запускает
      мутацию повторно и возвращает тот же результат; тот же ключ с другим
      телом — `409 idempotency_conflict` (`internal/platform/idempotency`).

## Явно отложено

- Полная версионная модель миссии с `stable_key` через несколько версий и
  сравнением требований — минимально жизнеспособный кусок сейчас: одна
  версия на миссию в этом срезе, `POST /missions/{id}/versions` для второй
  версии реализуется вместе со срезом 3 (изменение продукта), где она
  становится необходима.
- Реальный OIDC-провайдер в compose (Dex/Keycloak) — подключается перед
  первым внешним пилотом. Верификация JWT в `internal/platform/auth`
  реализована по-настоящему и проверена против тестового JWKS-сервера, не
  заглушена.
- Идемпотентность (`internal/platform/idempotency`) записывает результат
  мутации отдельной транзакцией после неё, а не в той же транзакции: узкое
  окно между ними означает, что крах процесса ровно в этот момент допускает
  повторный побочный эффект при retry, и два по-настоящему одновременных
  запроса с одним ключом до того, как первый успеет записать результат,
  оба выполнят мутацию. Закрыть оба случая означало бы, что каждый сервис
  модуля принимает готовую транзакцию снаружи вместо того, чтобы открывать
  свою — рефакторинг, который явно отложен. Тесты среза 1 покрывают
  последовательный повтор (реальный сценарий ретрая клиента), не гонку.
- SSE, экспорт, публикация — начиная со среза 2 и далее по таблице срезов.

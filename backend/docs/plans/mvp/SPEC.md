# Agent Arena — ТЗ на MVP первого соревнования

Исходная постановка от владельца продукта, 21 сентября 2026. Сохранена дословно: план в этом каталоге спорит и сверяется с ней. При расхождении плана и ТЗ — прав ТЗ, если в `00-overview.md` явно не записано обратное решение.

---

Ты работаешь в существующем репозитории Agent Arena: frontend на Next.js, backend на Go и PostgreSQL. Твоя задача — довести проект до работающего MVP первого соревнования. Нужно реализовать изменения, проверить их и обновить документацию. Одного плана недостаточно.

## Продукт и цель

Владельцы подключают своих coding agents. Агенты получают одинаковое задание, создают приложение и сдают результат. Платформа показывает работы, проверяет выполнение требований и объясняет результаты.

Первый законченный сценарий:

**Пользователь входит → создаёт агента → подключает его → выбирает конкурс → агент выполняет задание → сдаёт приложение → платформа проверяет работу → пользователь открывает результат и понимает оценку.**

Сохрани текущий минималистичный дизайн, страницы и выбранный стек. Не переписывай проект с нуля.

## Сначала проверь актуальное состояние

Прочитай инструкции репозитория, код, README и актуальные документы:

* `backend/docs/arena-backend-design.md`
* `backend/docs/plans/arena-slices.md`
* frontend: страницы, `lib/data.ts`, `lib/arena.ts`, `components/live-arena.tsx`, `components/artifact-preview.tsx`.

В проверенном ранее состоянии реализована основа backend: identity, agents, API-ключи, competitions, standings. Frontend использует статические данные; live-матч симулируется; submissions и judging ещё не реализованы.

Это исходное наблюдение, а не гарантия текущего состояния. Сохрани изменения, сделанные после него.

Составь короткий план и сразу переходи к реализации. Обычные технические решения принимай самостоятельно. Если внешняя интеграция требует недоступных credentials, продолжай остальные части и явно укажи, что осталось непроверенным.

## 1. Зафиксируй первую версию продукта

Для первого полноценного конкурса выбери создание небольшого веб-приложения. Используй существующую идею планировщика дня в незнакомом городе.

Подготовь одинаковый для участников набор данных: места, координаты, длительность посещения, часы работы и стоимость. Не требуй платных карт или внешних travel API.

Опиши проверяемые требования:

* пользователь задаёт доступное время и бюджет;
* приложение строит план из предоставленного набора мест;
* учитывает опубликованные ограничения времени и бюджета;
* позволяет удалить или заменить место и пересчитать план;
* сохраняет план после обновления страницы;
* объясняет ситуацию, когда подходящего плана нет;
* основной сценарий доступен на мобильной ширине.

Для первой версии разреши localStorage и явно напиши это в условиях. Уточни правила расчёта времени перемещения, чтобы решения можно было сравнивать.

Раздели обязательные требования и дополнительные достоинства. Скрытыми могут быть тестовые случаи, но не сами требования.

Обнови актуальный технический дизайн под эти решения. Макет frontend больше не является основанием для произвольных ограничений домена.

## 2. Соедини frontend с backend и реализуй участие

Замени статические данные на API в основном пользовательском сценарии. Моки сохрани только в явно обозначенном демонстрационном режиме.

Реализуй:

* вход через существующий OIDC-механизм;
* локальный воспроизводимый способ входа для разработки;
* создание агента;
* выпуск и отзыв API-ключа;
* показ полного ключа только при создании;
* страницу подключения с инструкцией и проверкой связи;
* кнопку участия на странице конкурса;
* состояния без агента, без работ, загрузки и ошибки.

Не показывай нового посетителя автоматически как Atlas.

Основной конкурс должен объяснять: что сделать, как подключиться, что сдавать, где выполняется агент, какие ограничения действуют и как оценивается результат.

## 3. Сделай минимальный работающий коннектор

Предоставь готовый CLI-коннектор, который пользователь запускает у себя.

Он должен:

* проверить API-ключ и показать имя агента;
* получить задание и условия конкурса;
* запустить указанную пользователем команду агента в отдельной рабочей директории;
* передать задание;
* показывать и отправлять безопасные события выполнения;
* получить результат в документированном формате;
* отправить работу;
* вывести ссылку на страницу результата.

Поддержи один реально проверенный coding agent и универсальный command adapter. Проверь актуальные флаги выбранного CLI по его документации. Не обещай поддержку остальных без проверки.

Credentials моделей остаются у владельца. Не отправляй секреты, переменные окружения и необработанные приватные логи на платформу.

Дай пример команды запуска и минимальный пример результата. Пользователь не должен сам писать реализацию протокола.

## 4. Реализуй сдачу и фиксацию работы

Добавь submissions, необходимые API, очередь проверки и отображение статусов.

Для приложения сохраняй:

* конкурс и агента;
* снимок версии/configuration агента;
* краткое описание;
* preview URL;
* URL репозитория и commit SHA;
* время сдачи;
* материалы и версию проверки.

Не считай изменяемый URL неизменяемым артефактом. Сохраняй доказательства, по которым выставлена оценка. Если соответствие deployment указанному commit не подтверждено, показывай это ограничение.

Один публичный профиль агента допустим. При этом каждая попытка должна сохранять свою конфигурацию: изменение модели в профиле не переписывает историю.

Предусмотри официальную попытку и тренировочные. Тренировочные не меняют официальный результат. Не смешивай повторные попытки после знакомства с заданием с первой попыткой.

## 5. Замени судью «по описанию» на проверку результата

Не оценивай функциональность, UX и качество кода только по summary и тексту HTML.

Минимальная схема:

**Проверки выполнения требований.**
Открывай приложение в изолированной браузерной среде и проверяй опубликованные пользовательские сценарии. Для первого конкурса реализуй конкретные проверки, без универсального framework для всех типов задач.

Не привязывай проверки к случайному DOM одного решения. Если нужны соглашения об элементах интерфейса или тестовом взаимодействии, опубликуй их в условиях.

**Доказательства.**
Сохраняй результат каждого сценария, ожидаемое и фактическое поведение, скриншоты и полезные диагностические материалы.

**Качественная оценка.**
LLM может анализировать доступные доказательства и давать объяснение. Он не должен заявлять о проверках, которые не проводились. Качество исходного кода оценивается только при наличии исходников; иначе критерий не оценён.

**Ручная проверка.**
Добавь простой административный способ подтвердить или исправить оценку с обоснованием. Это допустимая часть первого пилота.

Различай:

* проверка пройдена;
* проверка провалена;
* недостаточно данных;
* ошибка инфраструктуры.

Сбой проверяющего сервиса не означает поражение участника. Недоступную работу нельзя оценивать как работающую по её описанию.

Для внешних URL и браузера обеспечь запрет доступа к внутренней сети и metadata endpoints, ограничения времени и ресурсов, отсутствие секретов платформы. Контент работы считай недоверенными данными, включая инструкции, адресованные LLM-судье.

## 6. Сделай страницу результата главным экраном

Вместо заглушки preview показывай настоящий снимок приложения и ссылку на его запуск.

На странице работы должны быть:

* выполненные и проваленные требования;
* доказательства и объяснение оценки;
* отдельно функциональность и качественные оценки;
* сведения об агенте и версии;
* условия и время выполнения;
* источник данных о стоимости, если она известна;
* ограничения проверки.

Не выдумывай стоимость или проценты прогресса.

Добавь простое сравнение двух работ одного конкурса: preview, проверки и основные различия.

Очки за участие называй сезонными очками. Убери подпись Elo, если алгоритм Elo не реализован. Для MVP достаточно понятного рейтинга внутри конкурса; общие очки не должны изображать универсальный рейтинг качества.

Локальное выполнение не доказывает отсутствие помощи человека. Отрази это в правилах и статусе верификации.

## 7. После основного сценария подключи live-экран

Сохрани идею двух агентов в центре и очереди снизу.

Сначала реализуй один явно назначенный матч. Автоматический матчмейкинг отложи.

Подключи реальные события: начало работы, действия, доступность preview, завершение сборки, сдача, проверка, результат. Позволь агенту возвращаться к предыдущим этапам.

Убери случайный выбор победителя и вымышленный прогресс из рабочего режима. Демонстрацию оставь отдельно и подпиши.

Сохраняй события для воспроизведения матча. При отсутствии текущего матча показывай завершённый матч или понятное пустое состояние.

Не задерживай готовый основной сценарий ради сложной трансляции.

## Проверка готовности

Выполни сквозной прогон:

1. Администратор публикует конкурс.
2. Новый пользователь входит и создаёт агента.
3. Выпускает ключ и подключает коннектор.
4. Получает задание и сдаёт настоящую работу.
5. Проверка формирует результат с доказательствами.
6. Работа появляется в конкурсе и профиле.
7. Второй участник проходит тот же путь.
8. Их работы можно открыть и сравнить.

Отдельно проверь отзыв ключа, повторную отправку, дедлайн, недоступный preview и сбой судьи. Не допускай двойного начисления очков.

Сначала можно использовать тестового исполнителя для проверки инфраструктуры. До заявления о готовности интеграции выполни хотя бы один прогон с настоящим coding agent. Если это невозможно без доступа владельца — явно отдели проверенную инфраструктуру от непроверенной интеграции.

Проверь основные страницы в браузере на desktop и мобильной ширине. Запусти существующие тесты, typecheck и сборку. Не скрывай ошибки через `ignoreBuildErrors`. Интеграционные тесты, пропущенные из-за отсутствия Docker, не называй успешно пройденными.

## Границы работы

Пока не реализуй marketplace, платежи, переносимую репутацию, Kubernetes, несколько языковых лиг и сложную систему бейджей.

Не запускай произвольный код участников в процессе API. Не публикуй проект и не создавай платные ресурсы без отдельного указания.

Работай небольшими законченными этапами, сохраняй существующую функциональность и обновляй README по фактическому состоянию.

В конце предоставь:

* что работает;
* как поднять стенд и подключить агента;
* результаты проверок;
* что использует тестовые данные;
* реальные ограничения;
* следующий минимальный шаг до первого внешнего участника.

**Критерий успеха: внешний пользователь может пройти от входа до проверенной работы и понять причину своего результата.**

# Порядок реализации

Цель — последовательно получить работающий цикл приёмки, затем повторяемые испытания. Сроки разработки не фиксируются до выбора команды и инфраструктуры. Результат каждого среза можно проверить независимо.

## 1. Очерёдность

| Срез | Реализация | Критерий завершения |
|---|---|---|
| 0. Эталон задачи | Публичный snapshot города, stub API v1/v2, корректное приложение, намеренные поломки, сценарии | Каждый обязательный сценарий принимает эталон и обнаруживает соответствующий дефект |
| 1. Контракт и доступ | Go API, PostgreSQL, OIDC, приглашения, организация, кампания, версия миссии, аудит; минимальный React-кабинет | Владелец публикует контракт; чужая организация не читает его закрытые данные; контракт после публикации неизменен |
| 2. Сдача и приёмка | Загрузка, digest, запуск артефакта, независимый оценщик, свидетельства, матрица требований, решение и спор | Сданный извне пакет проходит полный цикл до принятого выпуска; повторная оценка использует те же байты |
| 3. Изменение продукта | Родительская сдача, миграция состояния, новые требования, повтор старых сценариев, история | Новый выпуск сохраняет данные старого; искусственная регрессия видна; исходная приёмка не стирается |
| 4. Управляемое исполнение | Один агентный адаптер, sandbox, очередь, lease, резерв, отмена, сверка и учёт помощи | Потеря worker не создаёт второй платный запуск; отмена подтверждена; расходы не теряются |
| 5. Сезон | Квалификация, два повторения, слепые сессии, правила баллов, арбитраж, очищенная публикация, передача | Полный эталонный сезон проведён по зафиксированному регламенту, включая случай без победителя |
| 6. Повторная кампания | Копирование брифа в новую версию, сравнение до/после, экспорт, второй адаптер по реальному спросу | Покупатель использует повторный результат для решения; стоимость подготовки и приёмки измерена |

Срезы 0–3 дают полезный ручной пилот. Срез 4 необходим для проверяемой управляемой автономности и сравнения наблюдаемых затрат. Срез 5 не должен задерживать получение обратной связи по первым принятым выпускам.

## 2. Первая инженерная задача

Реализовать путь **«владелец публикует миссию → участник сдаёт эталонный пакет → оценщик проверяет сохранение → владелец принимает выпуск»**.

В него входят три экрана: миссия, сдача и приёмка. API: создание кампании/миссии, открытие, загрузка/финализация, получение проверки и решение. Первые проверки — `/healthz`, сохранение после рестарта и изоляция двух пользовательских сессий. Хранение свидетельств и проверка tenant входят сразу: их трудно достоверно добавить к уже выданным результатам.

На первом срезе проверяются только доверенные fixtures. Запуск пакетов внешних участников включается после проверки изоляции сборки, приложения и браузера. Заглушка оплаты допустима, заглушка статуса «проверено» в реальном отчёте — нет.

## 3. Необходимые проверки реализации

| Риск | Проверка и ожидаемый результат |
|---|---|
| Подмена требований | Попытка изменить опубликованную версию отклоняется; новая версия не меняет старую приёмку |
| Чужой доступ | Пользователь второй организации не получает объект по ID, upload URL, экспорту или SSE |
| Подмена артефакта | Замена bytes после сдачи обнаруживается по digest; оценка не стартует с несовпадением |
| Неверный валидатор | Корректный маршрут с альтернативным порядком принят; маршрут с нарушением времени отклонён |
| Потеря данных | Адаптация разворачивается на состоянии build; удаление/порча сохранённого маршрута блокирует приёмку |
| Двойной запуск | Два одинаковых POST и повтор задания создают одну логическую попытку и одну внешнюю среду |
| Гонка бюджета | Два конкурентных запроса на последний резерв не проходят оба |
| Неопределённый ответ провайдера | После timeout создания ресурс ищется по execution_key; без подтверждения второй запуск запрещён |
| Потеря worker | После старта убивается worker; новый сверяет старую среду, просроченный fencing token отклоняется |
| Задержка расходов | Позднее измерение учитывается один раз, резерв не освобождается до сверки |
| Отмена | Среда действительно остановлена, ключ отозван; один только HTTP-ответ не делает run cancelled |
| Сбой платформы | Недоступный оценщик даёт error/pending, не fail и не нулевой конкурсный балл |
| Граница срока | Начатая до дедлайна, но завершённая после него загрузка не становится своевременной сдачей |
| Нестабильный результат | Один провал из двух обязательных повторений исключает конкурсный допуск; оба результата видны |
| Спор | Исправленный валидатор перепроверяет все затронутые артефакты; старое решение остаётся в истории |
| Публичная утечка | Отчёт не включает секрет, закрытый input, чужие сведения или прямую внутреннюю ссылку |
| Восстановление | Резервная копия восстанавливает связь требований, свидетельств, артефактов и решений |

Это задания на будущую проверку реализации, а не утверждение о пройденных тестах. Для текущего документного изменения проверяются только ссылки, структура и согласованность правил.

## 4. Решения, которые уже можно принять

- Ядро — контракт, неизменяемая сдача, независимая проверка, решение, история выпуска.
- Публичная и частная кампания используют одну модель данных и разные правила публикации.
- Начальная архитектура — модульный сервис управления с отдельными исполнителями и оценщиком.
- Официальные результаты привязаны к версиям условий и конфигурации; глобального рейтинга нет.
- Все денежные действия имеют резерв, идемпотентность и процедуру сверки неопределённого состояния.
- Первый домен — веб-приложение с одной интеграцией; первый сквозной пример — маршрут по городу.

## 5. Открытые решения и момент выбора

| Вопрос | Предложение по умолчанию | Когда блокирует работу |
|---|---|---|
| Язык backend | Go; при другой экспертизе команды доменная схема переносима | До начала среза 1 |
| Первый агент | Один, который реально принесёт участник; конкретный поставщик не выбран | До среза 4 |
| Sandbox-провайдер | Сервис одноразовых VM с отменой, квотами и поиском по execution_key | До выполнения внешнего недоверенного кода |
| Harbor | Проверить адаптер на одном артефакте; принять, если выполняет требования изоляции и учёта | До среза 4; срезы 0–3 не зависят |
| OIDC и хостинг | Выбрать по доступности команды и организации, без фиксирования облака сейчас | До внешнего пилота |
| Покупатель и интеграция | Один владелец API/SDK; городская задача использует stub до его появления | До коммерческого пилота |
| Права и публичность | Частный режим, пока нет согласованного публичного регламента | До регистрации внешних участников |
| Бюджет, тестировщики, арбитры | Предложения из регламента, затем фактическая смета и назначения | До открытия сезона |

Выбор облака, работающий runner и готовность платить не считаются установленными документом. Следующий завершённый инженерный результат — эталон и первый цикл приёмки; следующий продуктовый результат — решение реального владельца по этому отчёту.
